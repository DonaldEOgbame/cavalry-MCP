# Coverage: Cavalry Surface Reconciliation

This document tracks reconciliation between Cavalry's actual programmable surface
and the MCP's tool/capability inventory. It is a living record of *verified*
findings, not aspirational claims — every number here is either generated by a
script in `scripts/` or was checked against a live Cavalry 2.7.2 instance and is
noted as such.

## Two distinct surfaces, not one

Prior coverage work (`coverage/cavalry-api-manifest.json`) accounts for Cavalry's
**callable JS function surface**: 358 functions across `@JS_API`, `@JS_CORE_API`,
`@JS_GUI_API`, and `@JS_WIDGET_API`, parsed directly from
`/Applications/Cavalry.app/Contents/assets/MetaData/*_api_function_metadata.json`.
That inventory is complete for that surface (`unexplained: 0`, machine-checked in
`tests/unit/coverage.test.ts`).

It does **not** cover Cavalry's **node/attribute schema surface** — the set of
node types the engine can instantiate (as top-level layers, as children inside a
generator slot, or as render-queue items) and their attribute definitions. That
schema lives in a separate file Cavalry ships and was not previously ingested:

```
/Applications/Cavalry.app/Contents/assets/Definitions/nodeDefinitions.json
```

These are orthogonal axes. A single JS function, `api.setGenerator(layerId, slot,
type)`, is the reachability route for over a hundred distinct node types. Counting
node types as if they were missing "API methods" would double-count the same
underlying capability many times over — which is why the two are tracked as
separate manifests rather than merged into one number.

## Node-definition reconciliation

Generated by `scripts/generate-node-definition-coverage.mjs` into
`coverage/cavalry-node-definition-coverage.json`. Regenerate with:

```
npm run coverage:live-layer-types   # requires Cavalry running with the bridge loaded
npm run coverage:node-definitions
```

As of 2026-09-20 against Cavalry 2.7.2:

| Metric | Count |
|---|---|
| Total entries in `nodeDefinitions.json` | 483 |
| Abstract base types (not instantiable) | 47 |
| Concrete node types | 436 |
| Confirmed live via `api.getAllLayerTypes(true)` | 274 |
| Classified `STRUCTURED_MCP` (direct `layer_create`/`layer_create_primitive`) | 273 |
| Classified `GENERIC_MCP` (reachable via `generator_set` or a generic array attribute) | 163 |
| `UNKNOWN` | **0** |

`STRUCTURED_MCP` is 273, one more than the 274 live-confirmed layer types minus
overlap — `chartShape` could not be created directly as a top-level layer in a
live test and needed no reachability rule at all because it is a schema-only
internal child of `barChart`/`pieChart`; see caveats below.

### Why 172 node types aren't "missing"

`nodeDefinitions.json` records 436 concrete node types; only 274 are creatable
directly via `api.create`/`api.primitive`. The other 162 (after reconciling
`chartShape`) are not gaps — they are node types that only ever exist as a *value*
inside another node's generator/material/stroke/fill slot, or inside a generic
array-typed attribute. This was verified live, not assumed:

```
$ live probe: create a Duplicator, list its generator slots
duplicator#1 generatorSlots: ["generator","material","stroke"]
currentTypes.generator: "gridDistribution"   <- default distribution

$ generator_set(duplicator#1, slot="generator", type="circleDistribution") -> OK
$ generator_set(duplicator#1, slot="generator", type="fibonacciDistribution") -> OK
$ generator_set(duplicator#1, slot="generator", type="roseDistribution") -> OK
```

```
$ live probe: create a rectangle primitive, inspect its generator slots
basicShape#1 generatorSlots: ["material","generator","stroke"]
currentTypes.generator: "rectangleShape"    <- the primitive shape itself is a slot value

$ generator_set(basicShape#1, slot="fill", type="linearGradientShader") -> OK
$ generator_set(basicShape#1, slot="fill", type="noiseShader") -> OK
```

```
$ live probe: render queue item format switching
render_item_set_format calls api.setGenerator(itemId, "generator", formatType)
-> the same mechanism used for shapes/duplicators, applied to render formats
   (renderMP4, renderPNG, renderSVG, ...)
```

```
$ live probe: list all attributes on a rectangle layer
[... "filters", "deformers", "masks", "material.colorShaders", ...]
-> filters/deformers/masks are generic array-typed attributes on every layer,
   manipulated through attribute_set/attribute_get, not a dedicated function.
   There is no filter_list/filter_add operation in cavalry/bridge.js, and no
   filter-specific function exists anywhere in Cavalry's own API metadata either
   — confirming the array-attribute route is the only route, by design.
```

This confirms the project's stated design philosophy (`layer_create`,
`attribute_set`, `generator_set`, `graph_connect` as universal primitives rather
than one MCP tool per Cavalry concept) already reaches the overwhelming majority
of the schema surface without adding a single new tool.

### Per-superType reachability map

Classification is keyed by each node type's `superType` field in
`nodeDefinitions.json`. The full mapping and rationale for all 33 supertypes
found among the 172 non-top-level node types is in
`scripts/generate-node-definition-coverage.mjs` (`SUPERTYPE_ROUTE`). Only the
dominant categories were individually live-tested (distribution, primitive,
filter/array-attribute, gradient/noise shader slots, render format slots, chart
layers); the remaining supertypes were classified by the same structural pattern
(a `generator_set`-able slot on a parent node) but marked `verifiedLive: false`
in the JSON pending an explicit live check. That distinction is preserved in the
data — this document does not claim more verification than was actually done.

### Known caveat

`layer_create({ layerType: 'chartShape' })` failed live (`Cannot read properties
of null`). `barChart` and `pieChart` — the two `chartEngine` supertype nodes —
both create successfully as top-level layers, so end-user chart functionality is
unaffected, but `chartShape` itself as a schema entry could not be independently
confirmed reachable. This is flagged as `WORKFLOW_LIMITATION`, not
`PRODUCTION_BLOCKING`, since no known Cavalry workflow requires creating a bare
`chartShape` outside of the two chart layer types that already work.

## Open items carried forward

- Render format matrix (`coverage/render-formats.json`) still needs an actual
  live render + ffprobe pass per format; this pass only re-verified the JS
  function and node-schema inventories, not rendered output.
- The `verifiedLive: false` supertype routes above should be individually
  live-tested (create a node of each supertype's actual host layer, confirm the
  `generator_set`/`attribute_set` call succeeds) before being called fully
  proven rather than structurally inferred.
- Third-party plugin validation (Objective C) has not been attempted yet. The
  bundled filter plugins under `/Applications/Cavalry.app/Contents/assets/Plugins/`
  (Chroma Key, Bulge, Gaussian Blur, etc.) are visible live as
  `sceneGroup::<name>` layer types and are a plausible substitute for a true
  third-party plugin if no external one is available — this still needs to be
  attempted and documented per the plugin-test requirements.
